# Migrations

Drizzle ORM migrations for the shared PostgreSQL database.

Rules (see [CLAUDE.md](../../CLAUDE.md) §7.7):

- Every schema change is a new, versioned migration file generated by Drizzle Kit.
- An applied migration is never edited — a later change is always a new migration.
- No tenant-table migration is complete without its RLS policy in the same file — see
  [docs/architecture/database.md#row-level-security](../../docs/architecture/database.md#row-level-security).

[docs/architecture/database.md#migration-strategy](../../docs/architecture/database.md#migration-strategy):
extensions & roles; platform tables; CORE (RBAC, audit); CATALOG; QR; INVENTORY; location

endpoints exist yet, see [modules.md](../../docs/architecture/modules.md#sales-future--not-built-in-this-phase));
NOTIFICATIONS (outbox); idempotency; a NULLIF fix to the tenant-isolation policy helper; AUTH
(`auth_refresh_tokens`, Prompt 04 — server-side refresh-token store, see
[docs/architecture/security.md#authentication](../../docs/architecture/security.md#authentication));
CORE admin permissions (Prompt 05-A — six new `core.*` permission catalog rows for tenant/user/role

[ADR-0031](../../docs/decisions/0031-role-assignment-escalation-prevention.md)); CATALOG admin
permissions (Prompt 06 — `products.view`/`products.manage`/`categories.view`/`categories.manage`,

but no migration had ever actually inserted it). The CATALOG *tables* themselves (`products`,
`product_variants`, `categories`, `attribute_definitions`, ...) were already created by migration
`0003`, Prompt 02 — Prompt 06 only added the missing permission rows; it introduced no new tables.
INVENTORY admin permissions (Prompt 07 — `warehouses.view`/`warehouses.manage`/`locations.view`/
`locations.manage`, data-only, scoped strictly to roadmap.md's FASE 7; `inventory_balances`/

(`warehouses`, `locations`, `inventory_balances`, `inventory_movements`, `user_location_assignments`,
`inventory_transfers`, ...) were already created by migrations `0005`–`0007`, Prompt 02/02-A —
Prompt 07 only added the missing `warehouses.*`/`locations.*` permission rows and the application
layer (`apps/api/src/inventory/`) that reads/writes the already-existing `warehouses`/`locations`/

admin permissions (Prompt 08 — `inventory.view`/`inventory.adjust`, data-only, roadmap.md FASE 8

are reused as-is). QR public-resolver RLS (Prompt 09, migration `0018`) — three `*_public_resolve`
`SELECT` policies (`products`, `product_variants`, `locations`) for the `app_public_resolver` role,
plus the `locations` column-level `GRANT` those policies needed alongside them; not a new table
either — `qr_codes` itself was already created by migration `0004`, Prompt 02. This closes a real gap
between what `database.md#qr-codes`/`#row-level-security` already documented and what migration 0003
actually shipped (a `GRANT` with no matching row-level policy, so `app_public_resolver` could never
actually read a row) — see `database.md#qr-codes`'s "Prompt 09 finding, closed" note for the full
explanation. IMPORT worker role/claim support (Prompt 10, migrations `0019`–`0021`) —
`app_import_worker` Postgres role, `import_jobs.claimed_at`/`claimed_by` columns, and the matching
partial claim index; see the FASE 10 final report. ADMINISTRATION (FASE 11, migrations `0022`–`0024`)
— `tenant_settings` (tenant-scoped configuration, RLS) and `platform_admin_refresh_tokens`
(platform-scoped SuperAdmin session store, no RLS) in `0022`, plus a `GRANT INSERT ON audit_log TO

audit-write path existed before this phase); `administration.settings.view`/`.manage` permission
catalog rows (data-only) in `0023`; the `tenant_settings` `UNIQUE (tenant_id, id)`
composite-FK-target constraint (ADR-0018's universal convention, found missing by
`test/database/migrations.integration.test.ts`'s coverage check) in `0024` — a follow-up migration,
not a retroactive edit to `0022`. See [ADR-0032](../../docs/decisions/0032-platform-admin-authentication.md)
and [database.md#administration-tenant-settings-and-platform-admin-sessions](../../docs/architecture/database.md#administration-tenant-settings-and-platform-admin-sessions).
IMPORT worker tenant-status grant (PROMPT 011-B, migration `0025`) — `GRANT SELECT (id, status) ON
tenants TO app_import_worker`. SALES customers/cart/orders permission codes (FASE 12, migration
`0026`, data-only). SALES sales-returns permission codes (FASE 13, migration `0027`, data-only:
`sales.returns.view`/`sales.returns.create`; the return inspection/disposition half reuses
`inventory.returns.manage` and the exceptional-pricing workflow reuses
`pricing.discount.request`/`.approve`, all from migration `0001`). The `price_approvals`,
`sales_returns`, `sales_return_items` and `tenant_price_policies` *tables* were all created by
migrations `0003`/`0009`, Prompt 03 — FASE 13 added only the application layer and the two permission
rows; it introduced no new tables. See
[database.md#fase-13-application-behavior](../../docs/architecture/database.md#fase-13-application-behavior).
GLOBAL IDENTITY + TENANT MEMBERSHIPS (016-B, migrations `0028`–`0029`, database layer only — see
[ADR-0033](../../docs/decisions/0033-global-identity-tenant-memberships.md) and
[database.md#global-identity-and-tenant-memberships](../../docs/architecture/database.md#global-identity-and-tenant-memberships)):
`0028` creates `identities` and `tenant_memberships`, both platform-scoped (no RLS, same
access-by-GRANT-only posture as `tenants`/`platform_admins`/`platform_admin_refresh_tokens` —
`app_tenant` gets no grant on either). `0029` is an idempotent, deterministic backfill that
consolidates every existing `users` row into `identities`/`tenant_memberships` grouped by
normalized email (never by tenant): one shared `password_hash` per email consolidates into one
active identity; two or more *different* hashes for the same email produce one identity with
`status = 'pending_credential'` and a NULL credential — never an arbitrary pick. `users` (including
`users.password_hash`) is not modified by either migration; the current `tenantSlug`-based login is
unaffected. The email+password authentication flow itself (identity lookup, tenant selection,
`switch-tenant`, JWT changes) is a separate, later prompt.

ROLES/PERMISSIONS block (migration `0032`, data-only): `core.roles.manage` — one new permission
code closing `GAP-ROLE-CRUD` (custom role CRUD + per-role permission replacement), same
`module.action` pattern as 0014-0027. `roles`/`role_permissions` tables were already created by
migration `0002` (`0002_core_rbac_audit.sql`) — this migration introduces no new table. See
[database.md#rbac-roles-permissions](../../docs/architecture/database.md#rbac-roles-permissions)
and [ADR-0034](../../docs/decisions/0034-role-permission-self-escalation-prevention.md).

Each migration that creates a tenant-owned table also contains, in the same file: the table DDL
(generated by `drizzle-kit generate` from `apps/api/src/database/schema/`), `ENABLE`/`FORCE ROW
LEVEL SECURITY`, its `CREATE POLICY`, the relevant `GRANT`s, and the `set_updated_at`/
`prevent_tenant_id_change` triggers where applicable. The RLS policy and `ENABLE ROW LEVEL
SECURITY` statements are Drizzle-generated (native `pgPolicy`/`.enableRLS()` support); `FORCE ROW
LEVEL SECURITY`, `GRANT`, and trigger-attachment statements are hand-written, since Drizzle's
schema DSL does not model them.

## Applying migrations

```sh
pnpm --filter @saas-inventory/api db:migrate
```

Runs every pending migration, in order, as the `app_migrator` Postgres role (never as the
application's own `app_tenant` role) — see `apps/api/src/database/migrate.ts` and migration
`0000`'s header comment for the bootstrap requirement (the very first run needs a connection with
`CREATEROLE` + ownership of the target database).

## Regenerating (for a new schema change)

```sh
pnpm --filter @saas-inventory/api db:generate           # from the current TypeScript schema
pnpm --filter @saas-inventory/api db:generate --custom   # for a hand-written migration (e.g. a new trigger)
```
